Обновление 2026-10-01: авто переведено на модель через `ModelHeatDriver`.
Применение команд, повторы и смены драйверов проверяются на JVM; ядро сервиса
с `IgnitionSession`, `levels` и записью в CarService пока не извлечено.
Полевой долг сохраняется: `docs/model-control-checklist.md`.

Дата: 2026-09-14. Документ для продолжения в новой сессии — что сделано с
границами классов, что осталось и чего не нужно переоткрывать.

Тема отдельная от тепловой модели, но с ней связана: разбор `SeatHeatService`
и перевод авто-режима на модель проходят через один и тот же код, и делать их
надо одним заходом. Модель — в
`docs/superpowers/specs/2026-09-12-thermal-model-handoff.md`.

Ветка `docs/thermal-model-spec` от `master`.

## Что сделано

Пять коммитов, поведение не менялось ни в одном:

| | |
|---|---|
| `f92f423` | один путь чтения датчиков, один механизм отсева повторов в логе |
| `f6b492b` | `LogSink`, `Air`, `HeatSequence`, `Temperature`, `SeatHeatDriver`, `CalibrationSampler` |
| `4ab67d5` | роль `Diagnostics` для вкладки логов |
| `dd80b59` | роль `SeatControl` для вкладки сидений; `setSeatHeat` стал приватным |
| `0c4ccac` | `HeatNotification` и `ScreenBridge` |

**Новые классы:**

| класс | зачем |
|---|---|
| `LogSink` | был вложен в `AutoHeatEngine`; его пишут и модель, и ряд калибровки |
| `Air` | показания воздуха со временем получения; правило «достоверно 120 с» — правило модели, а не сервиса |
| `HeatSequence` | расписание задаёт и пользователь в пресетах, а не только таблица авто-режима |
| `Temperature` | `celsiusText` нужен пробнику и экрану; из-за него оба зависели от таблицы авто-расписаний |
| `SeatHeatDriver` | контракт «что ведёт подогрев обоих сидений» |
| `CalibrationSampler` | ряд калибровки со своим тиком и окном стоянки |
| `Diagnostics`, `SeatControl` | роли фасада: кто из вкладок что видит |
| `HeatNotification`, `ScreenBridge` | уведомление и мост к экрану |

`ModelShadow` отдаёт свой `Estimate` вместо `CalibrationLog.Model`: считающий
слой больше не знает про формат CSV. `SeatHeatService`: 751 → 593 строки.

**Тесты:** 136 на JVM. Впервые покрыты правила реплея экрана (`ScreenBridgeTest`,
5 тестов) и возраст показаний воздуха (`AirTest`, 2). Прежний
`SeatHeatServiceTest` распался на `AirTest` и `CalibrationSamplerTest` по новым
владельцам.

**Кто теперь что видит:** сервис целиком — только `MainActivity`
(композиционный корень) и `ServiceBindingController` (владелец binding).
Вкладки: логи → `Diagnostics`, сиденья → `SeatControl`, пресеты →
`PresetsPanel.Listener`, настройки → ничего.

## Что осталось: ядро сервиса

В `SeatHeatService` остаются ~200 строк, которые и есть настоящий менеджер
подогрева: `levels`, `IgnitionSession`, режимы, пресеты, `setSeatHeat`,
`syncSeatLevels`, `shutdownSeats`, `resume`. **Ни одного теста на них нет** —
`Service` на JVM не поднять, Robolectric в проекте нет, и написать тесты можно
только после извлечения.

Что делает извлечение дорогим:

- **`levels` — единственный источник правды, его трогают пять путей.**
  `setSeatHeat` за один вызов делает пять вещей в жёстком порядке: запись в
  машину → `session.seatsHeating()` → `levels.put` → уведомление экрана →
  строка ряда. Переставишь два — сломается либо экран, либо ряд, либо
  выключение по зажиганию.
- **Кольцо зависимостей.** Менеджеру нужен `probe` для записи в машину, `probe`
  нужен сервис как `Listener`, сэмплеру нужно состояние менеджера, менеджеру
  нужен `sampler.record`. Развязка требует ещё 2–3 мелких контракта
  (`SeatWriter` и подобные) — здесь легко переусложнить.
- **Порядок в `onCreate` завязан на голову.** `new CarHvacProbe(this, this)` в
  конструкторе уже коннектится и может синхронно позвать `log()`;
  `sampleSource` — поле-инициализатор, ссылающееся на `probe` и `modelShadow`,
  которые на момент его создания ещё `null`. Перестановка ломается тихо: NPE
  вылезет только на голове.

**Оценка:** полдня на diff, день на тесты (каскад по ON, выключение по OFF,
отказ записи, пресеты), плюс полный smoke на голове.

**Когда делать: вместе с переводом авто-режима на тепловую модель, не
отдельно.** Перевод пойдёт ровно через этот код — `resume`, `startAuto`,
`setSeatHeat`, `levels`. Разбор сейчас — два полных smoke вместо одного за одну
и ту же перестановку. Шов уже готов: поле сервиса имеет тип `SeatHeatDriver`,
и модельный драйвер подставляется в `onCreate` вместо `AutoHeatEngine`.

## Долг по проверке на голове

**Ни один из 26 коммитов ветки на физической голове не проверялся.** Вызовы
`android.car.*` в пяти коммитах этой сессии не менялись, но `CLAUDE.md`
требует smoke после правок вокруг них, а `CarHvacProbe` в `f92f423` был
переписан внутри (единый `read(verbose)`, `logOnce`).

Подробный чеклист с точными строками лога и отметками — в
`docs/field-checklist.html` (не в git по решению владельца). Кратко, что
смотреть при первом запуске:

1. лог после подключения: «CarHvacManager готов», «подписка на зажигание
   оформлена», «ряд калибровки: autoheat-data-…»;
2. кнопка «прочитать температуру» пишет три строки — салон, за бортом, ОЖ —
   **на каждое нажатие**, включая повтор (в снимке раз в 30 с первый отказ
   канала пишется один раз, дальше молчит);
3. зажигание ON → каскад стартует; OFF → оба сиденья выключаются, ряд встаёт
   на паузу через 5 минут;
4. экран, открытый после подключения, показывает готовность, температуру и
   уровни (реплей через `ScreenBridge`);
5. уведомление меняет текст на «Подогрев сидений активен» (`HeatNotification`);
6. переключение сегмента на «Пресеты» **не запускает** пресет само — только
   зажигание ON повторяет активный;
7. колонки модели в ряду и строки «модель, …» на месте.

## Решения, которые не нужно переоткрывать

- **`PresetsPanel` роли не получает.** Он уже ходит к сервису через собственный
  `PresetsPanel.Listener` — это и есть роль, объявленная у потребителя. Вторая
  поверх тех же четырёх вызовов была бы дублем, а не ISP.
- **Реализация `Diagnostics` остаётся в сервисе.** Пяти методам нужны `probe`
  (с переприсваиванием в `restartCarConnection`), `driver`, мост к экрану и
  ядро; отдельный класс держал бы обратные ссылки на всё — фасад поверх фасада.
  Интерфейс уже сделал полезное: сузил, кто их видит.
- **Lifecycle, `LocalBinder`, `intentFor`, `start` не выносятся** — это и есть
  `Service`.
- **`SeatHeatDriver` с одной реализацией — намеренно.** Заведён до второй,
  чтобы переключение было подстановкой, а не правкой пяти мест в сервисе.
- **Два одинаковых `withService`/`command` в двух контроллерах** оставлены
  копиями: 5 строк каждый, разные типы, общий generic-хелпер требовал бы
  отдельного класса. Появится третий — вынести.
- **`onLog` и `log` в сервисе — два имени одной операции** только потому, что
  так называется колбэк `CarHvacProbe.Listener`. Запись живёт в `log()`,
  `onLog()` — тонкий адаптер.

## Ошибки, которые уже были допущены

Чтобы не повторить:

- **`setMode` и возвращение по зажиганию ON — разные намерения.** Попытка
  свести их в один диспетчер дала бы запуск последнего пресета при простом
  переключении сегмента на «Пресеты». Развёрнуто обратно: `setMode` пресет не
  запускает, это делает только `resume`.
- **`SeatDriver` — неверное имя:** экземпляр один на оба сиденья, `Seat` идёт
  параметром. Префикс `SeatHeat` в проекте значит «оба сиденья»
  (`SeatHeatService`, `SeatHeatUiController`), `Seat*` — одно (`SeatObserver`).
- **`LogBuffer` предваряет строку отметкой времени.** Тест, проверявший префикс
  строки лога, падал не из-за кода. Искать по вхождению.
- **Сужение типа не делает UI-контроллер тестируемым.** `LogUiController`
  держит `Activity`, `View` и `Toast`; роль даёт узкий контракт, а не JVM-тест.
  Тестируемым стал `ScreenBridge` — потому что в нём нет Android.
- **Не всякая находка ревью стоит правки.** Перенос строки «температура: raw=…»
  из сервиса в `publishTemperature` пропущен: механизмы дедупа рядом похожи, но
  `lastCabinRaw` обновляется и на sentinel, а `loggedCabinRaw` — нет, и слияние
  добавило бы строку после каждого прогона 255.

## Пропущено намеренно (из ревью `/simplify`)

Найдено, признано верным, не сделано — с причинами:

- **семь геттеров `CarHvacProbe` → один `Readings`** и **`SeatObserver`: `base`
  + `histories` в один список** — переписывание контрактов далеко за пределами
  правок;
- **запись ряда и `saveLog` в фоновый поток** — реальный риск ANR через месяц
  эксплуатации, но это смена модели потоков в пути, чья семантика «flush на
  каждой строке» мотивирована мгновенным гашением ГУ; без проверки на голове
  не трогать;
- **тик не останавливается, если зажигание ни разу не пришло** (`parkedSinceMs`
  ставится только в `onIgnition(false)`) — изменение поведения, задача для
  `/code-review`, не для чистки;
- **файлы ряда копятся без потолка** — новая функция (ретенция), а не упрощение;
- **планы термостата не делят общий префикс** — 64 плана дают ~24 различных
  префикса, обход дерева дал бы ~4× меньше шагов. Валидацию из горячего цикла
  уже вынесли (`advanceValid`, −35 % расчёта); префиксы — следующий уровень,
  если на голове расчёт окажется медленным (порог лога `SLOW_UPDATE_MS = 100`).
