# Фоновый расчёт тепловой модели на голове

Дата: 2026-09-14. Статус: реализовано, на голове не проверено.

## Цель и границы

`SeatThermalModel` и `SeatThermostat` перенесены на Java, но ни к чему не
подключены. Параметры теплообмена не откалиброваны (handoff, раздел «Что
открыто»), поэтому управление по модели включать рано. Эта работа подключает
модель **в фоне**: наблюдатель ведёт оценку обоих сидений по фактическим
уровням, термостат считает решение, и всё это только пишется в ряд
калибровки и лог. В машину решение не уходит; авто-режим по-прежнему ведёт
`AutoHeatEngine`.

Смысл — проверить на голове то, что на JVM не проверить: сон, перезапуски
процесса, снимки между поездками, sentinel и достоверность входов. Для
подгонки параметров фон ничего не добавляет: ряд хранит всё нужное, модель
пересчитывается на компьютере. Когда калибровка будет готова, фон переводится
в управление без переделки наблюдателя.

Не входит: управление подогревом по модели, порог `T_off`, интерфейс на
экране, ветвление контакта посреди поездки, отдельный поток расчёта.

Ссылки: спецификация модели
`2026-09-10-auto-heat-thermal-model-design.md` (разделы 2, 3, 5, 6),
handoff `2026-09-12-thermal-model-handoff.md`.

## 1. Наблюдатель

Новый класс `SeatObserver` без ссылок на Android, по образцу
`IgnitionSession`: вся логика проверяется на JVM. Один экземпляр на сиденье.
Оба наблюдателя держит `ModelShadow` — тоже без Android (раздел 4).

### Профили

Банк из 18 гипотетических профилей раздела 6 спецификации переезжает из
`SeatThermostatTest` в `SeatObserver`; тест берёт его оттуда. Статус банка
не меняется: набор для поиска проблем, не калибровка.

| ось | варианты |
|---|---|
| теплообмен `p`, `r`, множитель `cₐ` | 43 / 1 / 1; 30.1 / 0.5 / 2; 55.9 / 2 / 0.5 |
| устройство уровней, доли 0…3 | ШИМ 0 / 0.40 / 0.66 / 1; уставки 0 / 1 / 1 / 1 |
| контакт: множитель `cₐ`, `cᵦ`, `B` | пусто 1 / 0 / —; слабый 0.75 / 0.02 / 32; сильный 0.5 / 0.08 / 35 |

Контакт профиля действует **только при зажигании ON**; при любом другом
зажигании кресло считается пустым (`cᵦ = 0`, множитель `cₐ` = 1).

- **Водитель** — 12 историй: 6 наборов теплообмена и уровней × слабый и
  сильный контакт. Пустой контакт при ON исключён допущением спецификации
  (раздел 2): режим привязан к ON, водитель на месте.
- **Пассажир** — 18 историй: все контакты.
- **Базовый профиль** — отдельная история: 43 °C/мин, `r = 1`, ШИМ, контакт
  пустой всегда. Это профиль, совпавший с «жарко» 12.09; его поверхность —
  одно число для сравнения с ощущением.

*simplicity:* посадка совпадает с ON, пересадок нет. Пассажир, севший
посреди поездки, в набор не входит. Путь апгрейда — ветвление контакта с
компонентной оболочкой (спецификация, раздел 2).

### Две границы

Для каждой истории хранятся нижняя и верхняя оценки `(мат, поверхность)`.
Пассивная схема с ограничителем уставки монотонна по состоянию, поэтому обе
границы продвигаются одними уравнениями и оболочка не рвётся. Инвариант:
нижняя ≤ верхней покомпонентно.

### Шаг

Наблюдатель досчитывает промежуток от прошлого обновления на каждом событии:
тик ряда, подтверждённая смена уровня, зажигание. Время — по
`elapsedRealtime`: сон головы входит в промежуток.

- **Уровень на промежутке** — последний подтверждённый автомобилем в этом
  процессе (записью или чтением, карта `levels` сервиса) либо взятый из
  снимка. Оценка `HeatSettings.manualLevel` подтверждением не считается.
  Если уровень сиденья не известен ни так, ни так, нижняя граница считается
  с уровнем 0, верхняя — с уровнем 3.
- **Окружение:** `E = 0.8·салон + 0.2·улица`; без достоверной улицы
  `E = салон`. Для промежутка берутся `E` в начале и в конце: нижняя граница
  считается с меньшим, верхняя — с большим. В поездке они почти совпадают,
  на стоянке это оболочка «воздух за перерыв неизвестен» (спецификация,
  раздел 3).
- **Контакт** — по зажиганию в начале промежутка. Событие зажигания делит
  промежуток.
- **Длинный промежуток** досчитывается кусками с остановкой, когда обе
  границы всех узлов сошлись со своим окружением до 0.01 °C при нулевом
  уровне. Это фактическое сближение, которое спецификация допускает, а не
  фиксированное время остывания, которое она запрещает. Результат совпадает
  с полным досчётом до 0.01 °C.
- **Устаревший воздух после перерыва.** После пробуждения голова ~50 секунд
  отдаёт салон прошлой сессии (замер 14.09), и перерыв, досчитанный по нему,
  был бы неверен. Перерыв длиннее 10 минут открывает двухминутное окно:
  воздух, вышедший за оболочку перерыва, расширяет её, и перерыв вместе со
  всем досчитанным после него (ON, смена уровня) прогоняется заново.
  Неизвестная история при старте строится от холоднейшего и теплейшего
  воздуха того же окна. После окна изменение воздуха — погода или печка и
  историю не переписывает. Это исполнение правила раздела 7 спецификации
  модели «пересчитывается при смене значения, а не фиксируется по первому
  отсчёту»; при согласовании дизайна оно было упущено.

### Неизвестная история

Снимка нет, он повреждён, версия не совпала или перерыв отрицательный:

```text
L = min(T_салон, T_улица) − 3        (без улицы — T_салон − 3)
U = max(T_салон, T_улица) + 3
нижняя = (L, L),  верхняя = (max(45, U), max(45, U))
```

Три гипотезы спецификации (остывшее, прогретое воздухом, недавно
грелось) укладываются в эту оболочку. Инициализация ждёт первого
достоверного воздуха.

## 2. Снимок между поездками

**Процесс жив** — снимок не нужен: наблюдатель в памяти, стоянка
досчитывается по `elapsedRealtime` при первом событии после неё. На этой
голове это основной случай: 12–14.09 процесс прожил 40 часов.

**Процесс перезапущен** — состояние восстанавливается из снимка.

- **Когда пишется:** при каждом обновлении наблюдателя — не реже раза в
  30 секунд в поездке, плюс события уровня и зажигания. Потеря при падении —
  не больше 30 секунд.
- **Где:** SharedPreferences, файл `autoheat_model`, ключи `snapshot_DRIVER`
  и `snapshot_PASSENGER`.
  Отдельно от `autoheat`, где пресеты и настройки.
- **Формат:** своя текстовая строка по образцу `Preset.encode`;
  кодирование и разбор проверяются на JVM.
- **Содержимое:** версия формата и банка, настенное время
  (`System.currentTimeMillis`), подтверждённые уровни, зажигание,
  последнее достоверное `E`, нижние и верхние состояния всех историй обоих
  сидений и базового профиля.

**Восстановление** при старте сервиса ждёт первого достоверного воздуха,
до этого решений нет. Перерыв — разница настенного времени. На перерыве
действует уровень из снимка: после подтверждённого выключения это 0; при
неподтверждённом верхняя граница честно продолжает греть. Окружение —
оболочка между `E` снимка и новым. Отрицательный перерыв, чужая версия или
ошибка разбора — неизвестная история.

*Потолок:* у головы может не быть часов с батарейкой. Скачок времени вперёд
после загрузки не обнаруживается — сиденье сочтут остывшим. Скачок назад
ловится как неизвестная история.

## 3. Решение фонового термостата

**Когда:** только при зажигании ON — и выбор, и проверка перегрева. Обычный
выбор — не чаще раза в 60 секунд по `elapsedRealtime`, на тике ряда.
Проверка перегрева `mustCoast` — на каждом тике (30 секунд). Наблюдатель при
этом досчитывает состояние при любом зажигании. Такт 15 секунд из
спецификации — требование к управлению; при переводе в управление он
вводится.

**В любом режиме сиденья** — ручном, пресетах, авто.

**Входы:**

- текущий уровень и время с его смены — фактические, подтверждённые
  автомобилем. Неизвестный уровень в плане считается нулём; первый увиденный
  в процессе уровень задержку повышения не запускает. Состояния наблюдателя
  идут по фактическим уровням, и план строится от них же: «что термостат
  сделал бы на месте текущего управления»;
- салон — последнее не-sentinel значение не старше 120 секунд с момента
  получения приложением, иначе `null` и решение 0 (спецификация, раздел 2);
- сценарии — нижняя и верхняя граница каждой истории сиденья: у водителя
  24, у пассажира 36; окружение сценария — текущее `E`.

**`T_off` не применяется.** Фон пишет чистое решение термостата; порог —
политика вызывающего и по колонке салона пересчитывается тривиально. Иначе
до зимы ряд содержал бы одни нули. При переводе в управление порог
применяет вызывающий.

### Что пишется

В ряд калибровки — по пять колонок на сиденье (префиксы `driver_`,
`passenger_`):

| колонка | значение |
|---|---|
| `…_base_lo`, `…_base_hi` | поверхность базового профиля, нижняя и верхняя граница |
| `…_bank_lo`, `…_bank_hi` | минимум нижних и максимум верхних поверхностей историй сиденья |
| `…_model_level` | последнее решение термостата; пусто вне ON или до первого решения |

Пустое поле — наблюдатель не готов. Формат одной цифры после запятой, как
`cabin_c`.

В лог — только изменения, буфер 500 строк:

- смена уровня или вида причины: `модель, водитель: 2 (план 2,2,2,1,1,1;
  поверхность база 34.1…34.1, банк 28.0…38.2)`. Новый план при том же
  уровне в лог не идёт — он меняется ежеминутно;
- `mustCoast` сработал (переход из «нет» в «да»): решение 0 с причиной
  `перегрев в прогнозе, ноль без ожидания минуты`;
- восстановление из снимка или неизвестная история, с длительностью
  досчёта;
- расчёт дольше 100 мс — с длительностью.

## 4. Ошибки, производительность, проверка

**Ошибки.** Фон не влияет на подогрев ни при каком сбое. Весь расчёт
внутри `ModelShadow.update` — в `catch (Throwable)`; первый сбой
пишет `ВНИМАНИЕ: фоновая модель отключена до перезапуска: …` и отключает
фон до перезапуска процесса. Каскад, пресеты, ручной режим и выключение по
зажиганию его не видят.

**Производительность.** Главный поток, как весь сервис. Замер на JVM
(ноутбук): решение по 36 сценариям пассажира — 7–18 мс, стоянка 40 часов —
17–53 мс. Голова медленнее; расчёт дольше 100 мс и длительность
восстановления идут в лог. Если на голове медленно, следующие шаги — отдельный
поток или точное решение линейной системы при нулевом уровне; сейчас не
делаются.

**Файлы:**

- `SeatObserver` — новый: банк, истории, границы, досчёт, окно пересчёта,
  сценарии, диапазоны, снимок;
- `ModelShadow` — новый, без Android: создание наблюдателей по первому
  достоверному воздуху, минутный такт решений, прогноз перегрева, лог только
  при смене, снимок через интерфейс `Store`, изоляция сбоев. Вынесен из
  сервиса, чтобы стык проверялся на JVM;
- `CalibrationLog` — десять колонок, тест формата;
- `SeatHeatService` — возраст воздуха (`reliable`), хранилище снимка в
  SharedPreferences, вызовы `ModelShadow` на тике, уровне и зажигании;
- `CarHvacProbe` — время получения улицы;
- `SeatThermostatTest` — банк из `SeatObserver`;
- `SeatThermalModel`, `SeatThermostat` — без изменений.

**Тесты на JVM:**

- нижняя граница ≤ верхней после нагрева, остывания и смены уровня;
  базовая траектория, посчитанная напрямую `advance`, внутри границ своей
  истории;
- стоянка с разным воздухом до и после: границы расходятся по оболочке;
- досчёт с остановкой по сближению совпадает с полным до 0.01 °C;
- контакт водителя: до ON пусто, после ON слабый/сильный; у пассажира
  пустой контакт остаётся;
- неизвестный уровень: нижняя граница с 0, верхняя с 3;
- неизвестная история: границы `(L, L)` и `(max(45, U), …)`;
- снимок: кодирование туда и обратно; повреждённая строка, чужая версия и
  отрицательный перерыв дают неизвестную историю;
- формат ряда с новыми колонками и пустыми полями.

Проверены мутациями: 12 в наблюдателе, 5 в окне пересчёта, 8 в
`ModelShadow`. Вызовы из сервиса на JVM не проверить; на голове — по логу: строка восстановления, строки решений,
отсутствие строки об отключении фона, заполненные колонки ряда.
